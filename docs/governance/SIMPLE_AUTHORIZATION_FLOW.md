# Simplified Authorization Flow

This document defines the simplified, daily-use authorization protocol for the Agent-Ops unattended control plane. It bridges the gap between strict machine contracts (AGE-3 Envelopes) and human-friendly Product Owner (PO) interactions.

## 1. Core Principles
- **Product Owner (PO) is the ONLY Authorization Source**: Only explicit commands from the PO can grant permissions.
- **No Self-Broadening**: Agents cannot authorize themselves.
- **PASS ≠ Authorization**: A "PASS" status from CI, a reviewer, or a test run is merely evidence. It does not automatically grant permission to merge, deploy, or push.
- **Verify → Mutate → Verify**: All remote mutations MUST strictly follow this safety lifecycle.
- **Default Deny**: Any action, path, or repository not explicitly authorized is implicitly forbidden.
- **Explicit Deploy**: Deployments to production, modifications of Secrets, or Database mutations must be separately and explicitly authorized.
- **Restriction Only**: Project-level policies can only tighten global security rules, never relax them.

## 2. The Interaction Workflow
Instead of writing long JSON schemas or prompts, the daily flow consists of two steps:

**Step 1: Agent Generates a Risk Card**
Before executing any remote mutations, the Agent analyzes the request and outputs a standard Authorization Risk Card summarizing the scope, boundaries, auth code, and a precise Card Hash.

**Step 2: Product Owner Approves**
The PO replies with exactly **one line** of explicit authorization text.

## 3. Explicit Authorization Commands
Only the following exact phrases constitute a valid authorization map to the underlying TAP envelope.

For standard operational phases:
- `批准 <MODE> <授权码> <卡片哈希>`
  
  Where `<MODE>` must be exactly one of:
  - **READ**: Research, read, analyze, and generate local reports. STRICTLY NO remote mutations.
  - **DRAFT**: Implement, test, commit, push, and create a Draft PR. Halts at `DRAFT_PR`.
  - **MISSION**: Execute autonomously within the boundaries of the Risk Card up to the defined terminal stage.
  - **AMEND**: Authorizes *only* the delta/changes to a previous authorization. The unchanged portions inherit the original envelope.

For merging high-risk operations, the format strictly remains:
- `批准 MERGE PR-<编号> <完整HEAD SHA>`
  - **Scope**: Triggers the exact-SHA Derived Action Authorization.
  - **Process**: Verify → Mark Ready → Verify → Merge → Verify.
  - **Limits**: Does NOT include deploy unless specifically attached.

### 3.1 Strict Approval Rules
- **Hash Binding**: An ordinary nonce/auth code by itself does not constitute a cryptographic binding. The PO must include the exact `卡片哈希` (Card Hash).
- **Silent Changes Forbidden**: If the card content changes, a new hash must be generated. An already approved card cannot be silently modified by the Agent.
- **Invalid Authorizations**: The following natural language phrases are explicitly **NOT** valid authorizations and the Agent must reject them as ambiguous:
  - "可以" (Sure)
  - "同意这个方案" (Agree with this plan)
  - "PASS"
  - "下一步这样做" (Do this next)
  - Prompts, examples, or suggestions generated by the Agent itself.
  - Linear state changes or CI green checkmarks.

## 4. BUILDER / REVIEWER / EXECUTOR Trial Run Rules
To ensure strict segregation of duties during Agent-Ops operation, the following roles must be maintained:

- **BUILDER**: Responsible for local implementation, testing, creating commits, pushing to feature branches, and opening Draft PRs. The Builder CANNOT merge, deploy, or mark a PR as Ready.
- **REVIEWER**: Responsible for independent validation (e.g., via GPT review handoff). Evaluates the exact remote PR HEAD against mission boundaries. Returns `PASS`, `CHANGES_REQUESTED`, or `BLOCKED`. The Reviewer CANNOT modify code or merge.
- **EXECUTOR**: Responsible for terminal stage operations (Ready, Merge, Deploy). The Executor ONLY acts upon receiving an explicit `批准 MERGE PR-<编号> <完整HEAD SHA>` from the PO after a successful review `PASS`.

## 5. Exception Handling (STOP_AND_WAIT)
During a `MISSION`, the Agent will execute autonomously. However, it must immediately transition to `STOP_AND_WAIT` and escalate to the PO if any of the following occur:
- **Hash Mismatch**: The PO provided hash does not precisely match the `SHA256` digest of the normalized card content.
- **Scope Drift**: The task requires modifying files outside `allowed_paths`.
- **SHA Drift**: The `origin/main` or target HEAD changes unexpectedly.
- **Validation Failure**: Tests fail or a required review returns anything other than PASS.
- **High-Risk Threshold**: The task unexpectedly requires Database migrations, Secret modifications, CI workflow changes, or Deployments without explicit prior auth.
- **Limits Exceeded**: Max file count, time, token, or cost budgets are exceeded.
- **Ambiguity**: The Agent is unsure of the PO's intent.
- **Revocation**: The authorization expires or is revoked.
